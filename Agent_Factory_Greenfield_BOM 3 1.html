COMPANION How this BOM relates to the Feature Cycle Model

These two documents describe the same delivery system from two sides, and neither is complete alone. The BOM is the agent specification: which agent runs, what it consumes, what it emits, which guardrails bind it, which quality gate scores it. The Feature Cycle Model is the human delivery rhythm: which role does what on which day of a five-day cycle, which ceremony happens when, and what “done” means. A phase in this BOM tells you what executes; a day in the Feature Cycle Model tells you when it executes and who is accountable for it.

These files live in two different repositories. The links below are relative and resolve when both repos are checked out as siblings under the same parent. If a link does not resolve, the canonical locations are agent-factory/presentations/ (this BOM, the agent catalog, the architecture and testing regimes) and ai-native/1-agentic-delivery-model/ (the feature cycle model and its worked example). Keep the phase ↔ day mapping below in sync whenever a phase is added, split or renumbered on either side.

PHASE 1 Requirements → Foundational Architecture → Impact Assessment → Dependency Graph

Why architecture moved into this phase. Requirements say what the system must do; they cannot say how many epics to create or where the boundaries lie. “Buyers order, producers list, the platform takes a fee” could be one epic or six — there is no principled basis without bounded contexts. With DDD applied here, each bounded context becomes an epic and the boundaries are non-arbitrary. The dependency graph is likewise not derivable from requirements alone — it derives from the component graph in the architecture, cross-referenced against requirements. Greenfield creates the foundational architecture; brownfield reads the application baseline in its place.

PHASE 2.25 Platform & Data Foundation — Cycle 0 RUNS ONCE PER PROJECT

Why this phase exists. The four architecture viewpoints run on different cadences. Application architecture changes roughly in proportion to features delivered; platform is ~80% front-loaded, integration ~50%, data ~40%. A feature cycle’s platform delta is empty most of the time and occasionally very large — a completely different shape from application architecture, and the reason platform cannot be a subsection of a per-feature HLD. Cycle 0 delivers no user-visible feature. Smuggling this work into the first real feature cycle is what makes that feature take three times its estimate and forces platform decisions under delivery pressure. Note the ordering dependency: L1-testing-env-provisioner in Phase 2.5 cannot provision environments until the platform exists, so 2.25 precedes 2.5.

Cycle 0 exit test: a trivial service can be built, deployed to production, observed, and can emit and consume an event — before any feature is attempted. If that is not true, Cycle 1 absorbs the platform work and corrupts every estimate after it.

PHASE 2.5 Test Foundation POLICY ONCE PER PI · REGISTERS EVERY CYCLE CLOSE

Why this phase exists. The original Phase 5 ran PI-wide, but scenario-writer reads stories.json — and stories only exist for committed features (Phase 3 is just-in-time). Test cases therefore cannot be authored up front. What can be settled up front is architecture-scoped and feature-agnostic: the tiering policy, the environments, the base fixture corpus, and the empty regression pack. Those four things live here; everything else moved into the per-cycle loop.

What this phase reads — and what it cannot. No hld.md exists at Phase 2.5 and none can: a component HLD is created by the first cycle that builds that component, so before Cycle 1 closes there are only deltas inside a cycle folder. This phase therefore reads the architecture declaration — the four Cycle 0 viewpoint documents: APP-2 (declared component map), PLT-1…5 (runtime topology), DAT-1/DAT-3 (entities, ownership, classification, retention), SEC-* (trust boundaries), REQ-* (budgets). That is not a workaround for an early-lifecycle gap: a stub registry derived from built components could never stub anything, because stubs exist precisely for components that do not yet exist.

Policy half vs register half. test-strategy.md is genuinely once per PI. stub-registry.json and the fixture corpus are registers — inventories of things not yet built — seeded here from the declaration and regenerated in the cycle-close chain (after arch-delta-merger, before gr-L1-architecture-conformance) from the merged canonical documents, never from a cycle folder. A stub-registry.json entry flips stub → real when that component's HLD and contract merge.

A feature cycle does not produce a standalone HLD. It produces a Feature Design Package: 00-overview.md — the only original content in the package (slice narrative, cross-component sequence diagram, viewpoint assertion table, NFR budget allocation) — plus a deltas/ folder in which every file has a named canonical destination, plus additive/ for journeys and wireframes, which are additive by nature and never merged. Nothing is authored twice, so nothing can drift.

Why HLD/LLD stay per-component. A feature genuinely spans frontend, backend, data and platform — but the design documents are scoped to the deployable, ownable component, not to the feature and not to the development type. (hld-buyer-spa.md beside hld-catalogue-service.md is a component split, not a frontend/backend split; the SPA is independently built, versioned, deployed and owned.) Per-feature HLDs would leave the Orders service described across six documents at six points in time, four of them superseded — an unusable baseline. Per-component documents alone would leave nobody owning the end-to-end flow — the part most likely to contain the defect. The FDP resolves both: vertical work order, horizontal canonical record, composed rather than duplicated. Data and Integration are not deployables, so their deltas target cross-component canonical documents instead.

Every design agent here runs in delta mode. Each takes the current canonical document as input — never a blank template — and emits a structured diff carrying type (additive / extending / structural), version_bump, structural and adr_required. Additive and extending deltas touch component documents only; structural deltas additionally propagate to foundational-solution-architecture.md and require an ADR plus Enterprise Architect approval. That asymmetry is what keeps the target stable enough to conform against. gr-L1-viewpoint-completeness blocks any FDP whose 00-overview.md omits one of the four viewpoints — a NONE with a stated reason passes, silence fails, because an omission is indistinguishable from an oversight.

PHASE 5 Test Design & Execution RUNS EVERY FEATURE CYCLE

Two structural changes from v2.0. (1) Ordering. Behaviour-level test authoring (scenario-writer → adversarial-case-writer → case-writer) now runs in Phase 3, before task-generator. Appendix C test T3 requires every Work Unit's verification_ref to "resolve to a concrete test/assertion/acceptance-criterion ID" — but in v2.0 the task-generator ran first, so those IDs (fbo-contract-02, oidc-unit-07) were invented with nothing to resolve against. Authoring cases first turns T3 from an aspiration into an enforceable foreign key. Cases derive from the Feature AC (which exists from Phase 2 decomposition), so they do not wait on design. (2) Execution. v2.0 generated scenarios, cases, scripts, fixtures and XRay entries and never ran them; testing-executor and defect-triager close that loop.

Split point — behaviour vs. executable. Behaviour artifacts (scenarios, Gherkin cases) need only the Feature AC, so they are authored in Phase 3 and gate the decomposition. Executable artifacts (Playwright/REST Assured scripts, fixtures) need the contract and the screen structure, so they are built in Phase 5 after design. This is what lets the code generators be handed a test oracle they did not write and may not edit.

“After design” is not “after merge.” The canonical services/<svc>/openapi.yaml does not exist yet — arch-delta-merger writes it at Stage 9, after the PR, after construction. A code-only agent, L1-testing-contract-resolver, therefore composes a resolved contract view from openapi.yaml@<from_version> ⊕ the cycle's delta — read-only, never written back — and hands it to script-generator, which never sees the two halves separately. Waiting for the merge would mean generating the oracle from the implementation, which is no oracle at all. The composition is proved against the running service at Stage 8 by contract-verifier (QG: contract-conformance 100%, blocking) — which is what makes reading intent safe here and forbidden for the baseline. Appendix J is the full ledger: what each of scenarios, cases and scripts may read, which architecture section supplies it, and what fourteen worked cycles actually consumed.

PHASE 7.5 Architecture Merge & Baseline Regeneration RUNS AT EVERY CYCLE CLOSE

Why this phase exists, and why it sits after the PR. The canonical architecture documents should move only once the change is real, so the merge runs after the PR lands — not at design time. This phase is what makes a feature cycle’s output accumulate into something coherent instead of leaving N contradictory design fragments behind. It is also where the two-document regime is maintained: the foundational solution architecture is the target (normative; rationale, options considered, ADR references; moves only on structural deltas) and the application baseline is the current state (descriptive; versions, owners, CMDB ids, evidence; regenerated every cycle). They share an identical section-ID spine so they are mechanically diffable, but each carries fields the other must not — same spine, different payload.

The gap between target and baseline is the drift register — and it is an asset. It distinguishes implementation drift (the build diverged from approved intent → remediation backlog item with an owner and a target cycle) from unbuilt target (intent legitimately ahead of implementation → roadmap visibility, not a defect). Without both documents you cannot tell these apart: a single merged document silently rewrites intent to match whatever was built, which means architectural violations become invisible the moment they ship.

PHASE 8 Integration, Regression & Release Testing CADENCE LOOP — BAND BOUNDARY / EVERY 2 CYCLES / RELEASE

The cadence tier. Three distinct triggers, deliberately not merged: band boundary fires true cross-feature E2E integration (Appendix E already names the band boundary as "the shared synchronisation beat where their contracts reconcile"); every 2 cycles (~10 days) fires a risk-selected regression run; release fires the full pack plus the NFR suites. The regression pack is centrally managed by a single curator agent and is augmented at every feature close.

Why selection is mandatory, not optional. A pack that only ever grows will, within a PI or two, stop finishing inside the cadence window — at which point teams start skipping it, and the regime silently dies. risk-selector keeps the fortnightly run bounded by choosing a subset from blast radius and change diff; regression-pack-curator keeps the pack itself bounded by deduplicating, re-tiering, quarantining flakes and retiring cases for removed behaviour. The pack must be able to shrink.

APPENDIX C Decomposition Standard — the rubric feature-decomposer & task-generator decompose against

Why this exists

The inherited Jira ladder (Epic → Feature → Story → Task) was built to solve a human coordination problem, not an agent execution problem. It conflates two things that pull in opposite directions: human governance granularity (the levels at which a human states intent, prioritizes, and approves — wants to be coarse) and agent execution granularity (the level at which an agent reliably picks up and completes work — governed by context, not effort). This standard separates the two and gives the decomposer agents a concrete, testable rubric.

Governing rule: decompose to the coarsest level at which each unit is still independently verifiable and context-bounded — and no finer. Over-decomposition is a named failure mode: units too small create coordination overhead, lose the thread of the larger goal, and burn more orchestration/tokens than they save.

C.2 — The collapsible-story rule

A user story was always two things wearing one hat: (a) a vertical slice of value, and (b) acceptance criteria in narrative form. In the ADLC these separate cleanly:

• The acceptance criteria attach directly to the Feature — agents consume Given/When/Then perfectly well without the "As a… I want…" wrapper.
• The vertical slice only needs its own level when a feature genuinely won't fit one cycle — at which point a "story" is a sub-feature.

Decision: the feature-decomposer emits a needs_slicing flag. If a feature passes the "fits one cycle" test, no story layer is created and story-generator elaborates Work Units straight from the feature's AC. If it fails, the decomposer emits Story (sub-feature) rows first, each of which independently re-runs the same fit test.

APPENDIX F Output Contract — regression-pack.json (the centrally-managed pack)

G.6 — Answering the two design questions directly

“All at once before cycles, or per cycle?”

Split. Only the strategy layer runs up front (Phase 2.5: four agents, one pass) — tier policy, environments, base fixtures, empty pack. Everything case-specific is per cycle, because under just-in-time elaboration the stories, AC and API contracts that test cases must ground in do not exist until the feature is committed. Authoring the PI's test cases up front would ground them in designs that had not been produced, and they would be stale by the time the code was built.

“What is the right order?”

Cases before Work Units; behaviour before design; design before scripts; scripts before code; code before execution; execution before promotion. Behaviour-level cases need only the Feature AC, so they gate decomposition (Stage 2 → 3). Executable scripts need the contract, so they follow design (Stage 4 → 5). Construction then builds against an oracle it did not author and cannot edit (Stage 6), and only a green feature pack plus clean contracts promotes cases into the central regression pack (Stage 9).
Net change in v2.1: 12 net-new agents · 2 net-new guardrails (gr-L1-verification-ref-resolvable, gr-L1-test-immutability) · 6 net-new quality gates · 6 net-new tool integrations · 1 net-new output contract (Appendix F) · Phase 5 split into Phase 2.5 + Phase 5 · new cadence Phase 8. The four testing tiers you asked for map to: feature = Stage 7 (every cycle) · contract = Stage 8 (every cycle) · integration = Phase 8 (band boundary) · automated regression + NFR = Phase 8 (every 2 cycles / release).

I.0 — Requirements & architecture: what does not run, and why

This is the shortest section in the three appendices, and that is the point. A bugfix has no requirements elaboration and no architecture stage at all — not because the track is sloppy, but because the reproduction test does the work all of them would have done. It is executable, unambiguous about what is wrong, and states exactly when the job is finished. A PRD would restate it in prose; a baseline read would scan an architecture to locate a defect already located to a handful of files.

The escalation rule is what makes the omissions safe. Every stage dropped above rests on one assumption: the defect is scoped to a handful of files inside an existing capability. Requirements & architecture across the three tracks, in one line each. G (greenfield) authors both from nothing: vision → PRD, then principles → four-viewpoint target → Cycle 0 — and the architecture is what makes the epics non-arbitrary. H (brownfield) shrinks requirements to a feature brief and inverts architecture from output to input, reading baseline and target so a locally reasonable change cannot silently entrench drift. I (bugfix) drops both entirely and lets one failing test carry the whole specification — with an escalation path back to H the moment that stops being enough.

I.4 — Which architecture documents a bugfix can touch — and the three cases where it does

Stage 8 says “conditional, skipped by most bugfixes, and that is correct.” This section says exactly when it is not skipped. The rule is narrow on purpose: a fix restores intended behaviour, so by definition it cannot diverge from the target — and therefore cannot need an architecture delta. The exceptions are the cases where restoring behaviour turns out to require changing a contract, a schema, or a platform setting, all of which are facts the baseline records.

DocumentFrequencyThe case where it firesWhat happens — and when it escalates instead
integration-architecture.md
INT-2 / INT-4		 Most common
of a rare set		 The fix changes an API response, a status code, a field, or an event payload — because the documented contract and the actual behaviour disagreed, and the behaviour was the defect. The distinction that decides the track. Non-breaking — the contract is corrected to what consumers already relied on, or an optional field is added: stays on this track, INT delta merged at Stage 8. Breaking for a live consumer — re-raise on Appendix H. It is then a versioning decision (expand-and-contract or a coordinated release), not a fix, and it needs the impact assessment and consumer coordination that only the brownfield track provides.
data-architecture.md
DAT-1 / DAT-3		 Rare The defect’s cause is the schema: a missing unique constraint that allowed duplicates, a column type that silently truncated, a nullable field that should never have been. The fix is a migration, not a code change. DAT delta merged at Stage 8; tool-L1-db-schema-diff provides the evidence. Escalates to Appendix H if the migration is not backward-compatible or touches a table outside scope — at which point Appendix C test T2 has failed and it was never a bugfix. If the fix introduces or reclassifies PII, DAT-3 moves and gr-L1-pii-detection blocks.
platform-architecture.md
PLT-1 / PLT-4 / PLT-5		 Rare Never via PLT-6 — a bugfix does not introduce a new capability class. It fires on a setting the baseline records: a timeout or memory limit that caused the defect (PLT-1), an alert that never fired or an SLO never defined (PLT-4), a retry or failover behaviour that did not hold (PLT-5). PLT delta merged at Stage 8. These are the bugfixes most often missed: the code is fine, the configuration was wrong, and with no delta the baseline keeps claiming a timeout the system no longer uses. A PLT-4 fix is frequently the highest-value output of an incident — the alert that should have caught it.
All three — the default No architecture change whatsoever. The overwhelming majority of bugfixes correct logic inside one component: Stage 8 is skipped, the canonical documents are untouched, the baseline is not regenerated, and the only lasting artifact is the promoted reproduction test in the regression pack. That is the correct and expected outcome — forcing a baseline regeneration per bugfix would make the track too expensive to use, and teams would route defects around it.
How Stage 8 decides, mechanically. It does not ask “did we change architecture?” — a question agents answer badly. It asks three checkable questions against the diff: (1) did openapi.yaml or an event schema change? → INT. (2) did a migration file appear? → DAT. (3) did an IaC, config or alerting file change? → PLT. All three negative — the common case — and Stage 8 is skipped outright. This is the same design as the PLT-6 capability register: replace a judgement call with a lookup.
The asymmetry worth naming. On Appendix H the architecture documents are opened by intent — the impact assessment decides at Stage 1 what will change, five stages before it is written. On Appendix I they are opened by discovery — nobody plans a schema or contract change into a bugfix; it emerges from the diff at Stage 8. That is why H detects early and I detects late, and why I’s detection has to be mechanical: there is no earlier stage in which someone could have thought about it.

Why Stage 7 is the highest-value step on this track

A bug that happened once is the best evidence you will ever get about where this system is fragile — and the reproduction test is that evidence in executable form. Without promotion it lives only in the fix commit and protects nothing after the branch merges, which is exactly how the same defect class returns two quarters later in a neighbouring code path. A risk:high repro case, once in the pack, is thereafter never excluded by risk selection on any track.

The two prohibitions that make the track safe

The fix agent may not touch a file outside the scope triage drew, and the verify agent may not edit the reproduction test to make it pass. Remove either and the track stops being trustworthy: the first prevents a one-line fix becoming an unreviewed refactor, and the second is the entire difference between a green suite that means something and one that does not. Both are the same rules as G and H — gr-L1-test-immutability and scope discipline — just at their smallest possible expression.
When a bug is not a bugfix. If triage cannot scope the defect to a handful of files (T2 fails), or the fix requires a contract change, or the cause turns out to be a missing capability rather than a broken one, the work is re-raised on the brownfield track (Appendix H) — where it gets impact assessment, coverage-gap analysis and characterisation pinning. That escalation is a normal outcome, not a failure. The cost of getting it wrong is a change that skipped impact assessment entirely.
