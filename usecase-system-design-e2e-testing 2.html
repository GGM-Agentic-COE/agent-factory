End-to-End Testing — Agentic System Design

A 19-agent orchestrated workflow that authors, builds, executes, triages and curates the test estate across three development scenarios. This document is the implementation contract: every agent's inputs, outputs, knowledge bases, tools and guardrails are specified here, per stage, per scenario.

The one design constraint everything else follows from. The test estate must be an oracle — an independent statement of what correct means. That independence is not a policy anyone has to remember; it is a consequence of which document each agent is given. Scenario and case agents read acceptance criteria and architecture rules and are denied the contract, the HLD and the source. Script agents read the contract because they cannot function without it, and a later blocking stage proves what they produced against the running service. Every input list in §2 and §3 is enforcing that line.

2.2 Brownfield — the inverted regime

T-A and T-B do not re-run — the strategy, environments and pack are inherited. Two stages exist that greenfield has no analogue for, and both run before a single existing line is modified. Greenfield asks “does the new thing work?”; brownfield asks first “what does the existing thing already do, and what currently protects it?” — because the regression pack covers only what someone previously chose to cover, and the code most likely to be changed is frequently the code least covered.

Why a wrong behaviour is pinned anyway
Design ruleA pin records what the system does, not what it should. Where current behaviour is the defect, the pin is written and tagged characterization:suspect — otherwise the change has no baseline against which to demonstrate it fixed anything, and “it works now” rests on nobody having written down what “before” looked like.

An agent cannot distinguish an accidental fix from an accidental break. That is why the untagged case blocks and the tagged case is checked against its linked defect.

2.3 Bugfix — two testing steps, and a mandatory exit

Four agents, not eighteen. The track is defined by what it omits — no PRD, no elaboration, no impact assessment, no coverage-gap analysis, no characterisation pinning, no delta set, no baseline regeneration. Every one of those omissions rests on a single bet: the defect is confined to a handful of files inside an existing capability. So the track's most important element is not a stage at all — it is the test that decides whether the bet still holds, and the exit it takes when it does not.

BUGFIX LIFECYCLE 4 AGENTS · 1 MANDATORY EXIT

A Task-level defect produces no cycle folder, no deltas and no baseline regeneration. Forcing those per defect would make the track too expensive to use, and teams would route defects around it — and a track nobody uses records nothing.

X-2 · The scope test — the exit
Three checks, any one ends the track T2 scope — confinable to a handful of files inside an existing capability? A migration has no boundary.
Contract change — does a published contract's shape change, or a live consumer's pact break? That is a versioning decision, and this track has no stage at which one is made or approved.
Missing capability — does the fix need something not AVAILABLE? Provisioning has lead time; discovering it at construction is five stages too late.

→ ESCALATE to brownfield. Suppressing the escalation is this track's one catastrophic failure mode: it produces a change that skipped impact assessment, coverage-gap analysis and characterisation entirely — and nothing about it looks wrong in review.

Step 8 — promoting the reproduction test — is the step that pays for this track. A defect that happened once is the best evidence you will ever get about where this system is fragile, and the reproduction test is that evidence in executable form. Without promotion it lives only in the fix commit and protects nothing after the branch merges — which is exactly how the same defect class returns two quarters later in a neighbouring code path.

3. Agent Specifications

Full cards for the seven agents whose design decisions are load-bearing. The remaining twelve are specified in the same shape in agents/<id>/spec.yaml; §2 gives their inputs, outputs, KBs, tools and guardrails, which is the reviewable surface.

Agent 1: Test Strategy Architect — LLM

Role:Settle the testing regime for a whole PI — tiers, criteria, targets, topology, governance. Authors no test cases.
Input:prd.md, nfr_classifications, roadmap.md, and the four Cycle 0 viewpoint documents. Never hld.md — it does not exist at this point.
Output:test-strategy.md — fields: tiers[], entry_exit[tier], coverage_targets, tooling, env_topology, nfr_approach, pack_governance{flake_threshold, staleness_ceiling, runtime_budget_per_tier}.
Knowledge Bases:kb-L1-testing-standards (~6k) · kb-L1-enterprise-architecture (~8k) · kb-L2-food-regulatory (~5k)
Prompt Strategy:CoT with structured-JSON output for the governance block, prose for the rationale sections. Few-shot with 2 prior approved strategies.
Model:Claude Opus 5 — runs once per PI and its output constrains 18 agents for months; the highest-leverage, lowest-frequency decision in the workflow.
Token Budget:Instructions 3k + KB 19k + Input 14k + Output 6k = 42k · 21% of 200k
Temperature:0.2 — policy authoring; consistency across revisions matters more than variety.
Inline Quality Gates:Every tier must declare entry and exit criteria; every governance threshold must be a number. A prose threshold fails schema validation.
Error Handling:Schema failure → one retry with the validator output appended. Second failure → halt the PI's testing setup and route to the QA Expert. There is no safe default strategy; guessing one would silently constrain every later agent.

Agent 2: Adversarial Case Writer — LLM

Role:Generate the failure modes acceptance criteria do not describe — negative, boundary, abuse and NFR — by reading the architecture rules directly.
Input:test-scenarios.md, nfr_classifications, regulatory posture, impact-assessment.md, and APP-3 INV-* / CON-* / SEC-* / REQ-* read live from the canonical documents. Brownfield adds coverage-gap.json and the drift register.
Output:test-scenarios.adversarial.md — each entry: {id, polarity, derived_from, rule_citation, tier_hint, risk}. rule_citation is mandatory.
Knowledge Bases:kb-L1-testing-standards (~6k) · kb-L1-enterprise-security (~7k) · kb-L2-food-regulatory (~5k)
Prompt Strategy:CoT, structured JSON. Few-shot with 4 examples chosen to demonstrate the invariant-vs-validation distinction, which is the error this agent exists to prevent.
Model:Claude Opus 5 — accuracy-critical. A missed compliance failure mode is not caught downstream by anything; it simply never gets tested.
Token Budget:Instructions 4k + KB 18k + Input 22k + Output 9k = 53k · 27% of 200k
Temperature:0.6 — deliberately higher than any other agent. Adversarial generation is the one place in this workflow where coverage of the unexpected beats determinism.
Inline Quality Gates:At least one adversarial case per compliance-tagged AC clause. Shortfall is a hard fail, not a warning.
Error Handling:A case citing a rule that does not exist is dropped by gr-L1-hallucination-check and logged with the fabricated citation. If more than 20% are dropped, the whole output is rejected and routed to the QA Expert — a high fabrication rate means the KBs are stale, and no retry fixes that.

Model:Claude Sonnet 5 — high volume, mechanical transformation, no judgement call that Opus would make better.
Token Budget:Instructions 3k + KB 6k + Input 18k + Output 14k = 41k · 21% of 200k
Temperature:0.1 — near-deterministic. Two runs over the same scenarios must produce the same cases.
Inline Quality Gates:qg-L1-test-case-ac-coverage ≥8 — every AC clause maps to at least one case.
Error Handling:An amendment without a cited AC clause is rejected by gr-L1-test-immutability before it is written. A characterisation pin can never be amended by this path at all — an agent cannot distinguish an accidental fix from an accidental break.

Agent 4: Contract Resolver — code-only · runs immediately before the script generator

Role:Compose the resolved contract view that T-D generates against, and refuse to compose it when the base has moved.
Input:The cycle's openapi-<svc>.delta.yaml (carrying target_document and from_version) and the canonical services/<svc>/openapi.yaml read at that exact version.
Output:<cycle>/resolved/openapi-<svc>.resolved.yaml, headed GENERATED — NOT A SOURCE OF TRUTH with its provenance and the versions it composed. Three resolution shapes: creating (from_version: null → the delta is the contract), extending (base ⊕ new paths), modifying (overlay at operation level — not concatenation).
Knowledge Bases:N/A (code-only agent)
Prompt Strategy:N/A (code-only agent)
Model:N/A (code-only agent) — and this is the design decision, not an omission. A YAML overlay is deterministic. Handing it to a model would (a) let it invent an endpoint that is in neither the base nor the delta, (b) turn a hard from_version boolean into a judgement a model can be argued out of, and (c) double the script generator's input by passing both halves in. Composition is arithmetic; only the code that does it can be trusted to be exact.
Token Budget:N/A (code-only agent). It reduces the script generator's budget by handing over one composed document instead of two.
Temperature:N/A (code-only agent)
Inline Quality Gates:gr-L1-from-version-match — BLOCKING. The result must also parse as valid OpenAPI; an overlay that produces a duplicate path key or an invalid operation fails here, not three stages later in a script that will not run.
Error Handling:Refusal is the designed outcome, not an exception. A from_version mismatch emits resolution-refused.json naming the declared version, the actual version and the cycle that moved it, and routes to the Feature Owner: “this cycle was authored against an architecture that has since changed.” It surfaces on Day 2, where re-authoring a delta is cheap, rather than at merge on Day 5, where it is a conflict. There is no fallback and no retry — composing against the wrong base is worse than not composing at all.

Why this is a separate agent rather than a step inside the script generator: the resolved view has a second consumer. Brownfield provider-mode contract verification needs the base half to establish what a consumer is entitled to today, and reusing one resolver keeps both stages composing the same way from the same inputs.

Agent 5: Script Generator — LLM

Role:Turn cases into executable automation against a contract that has not been merged yet.
Input:test-cases.feature; openapi-<svc>.resolved.yaml as handed over by contract-resolver; wireframes.md; stub-registry.json. It never sees the delta or the base separately, so it cannot compose them differently.
Output:Playwright / REST Assured source, one file per tier, every test annotated with its case_id.
Knowledge Bases:kb-L1-testing-standards (~6k)
Prompt Strategy:Few-shot (3 per framework), structured file output. The resolved view arrives pre-composed — the model performs no merging.
Model:Claude Sonnet 5 — code generation against a known contract and known selectors; cost-sensitive at this volume.
Token Budget:Instructions 4k + KB 6k + Input 26k + Output 20k = 56k · 28% of 200k. The resolved view is the largest input and grows with the service; if it exceeds ~40k, scope the view to the paths this cycle's cases actually call.
Temperature:0.1 — generated code must be stable across runs so review diffs stay meaningful.
Inline Quality Gates:Every emitted test carries a resolvable case_id; every referenced endpoint exists in the resolved view.
Error Handling:This agent never reaches invalid input: contract-resolver has already refused a moved base and rejected an unparseable overlay. Its own failure mode is a script that does not compile — caught by the executability check, retried once with the compiler output, then routed to the QA Expert.

Agent 6: Defect Triager — LLM · the agent that makes the loop terminate

Role:Independently classify every failure and route it. Exists so that a construction agent handed a red suite cannot take its one cheap move — weakening the assertion.
Input:test-execution-report.json failures, the implicated source fetched on demand, case-index.json.
Output:triage-verdict.json — {case_id, verdict, target_agent, rationale, ac_citation?}. Verdicts: code_defect · test_defect · data_defect · env_defect · flake.
Knowledge Bases:kb-L1-testing-standards (~6k)
Prompt Strategy:CoT with a forced rationale field, structured JSON. Few-shot with 5 examples, at least one per verdict class.
Model:Claude Opus 5 — the verdict decides whether code or the test changes. A wrong test_defect erodes the oracle permanently, so this is the most consequential classification in the workflow.
Token Budget:Instructions 4k + KB 6k + Input 30k + Output 4k = 44k · 22% of 200k
Temperature:0.0 — a classifier. The same failure must always produce the same verdict, otherwise triage cannot be audited.
Inline Quality Gates:A test_defect verdict without an ac_citation is invalid on its face and rejected before routing.
Error Handling:Three consecutive triage passes on the same case_id without the suite going green → escalate to the Feature Owner. Oscillation is the failure mode; the counter is what stops it. characterisation_break is never auto-resolved at all.

Agent 7: Regression Pack Curator — LLM + code · sole writer of the pack

Role:The single writer of regression-pack.json for the life of the product — init, promote, curate. Written by exactly one agent so promotion, re-tiering and retirement are auditable in one place.
Input:Cycle cases + execution history + existing pack + governance rules. Curate mode additionally reads flake signals from triage-verdict.json.
Output:regression-pack.json, XRay test-set updates, pack-changelog.md with one entry per cycle.
Knowledge Bases:kb-L1-testing-standards (~6k)
Prompt Strategy:Structured JSON. Deduplication and tiering are LLM judgements; retirement and quarantine are code-only rule applications against the thresholds — a model must not be able to decide to drop a case.
Model:Claude Sonnet 5 for the judgement half; the enforcement half has no model.
Token Budget:Instructions 3k + KB 6k + Input 24k + Output 10k = 43k · 22% of 200k. Input is capped by passing pack summaries plus the cycle's cases, never the whole pack.
Temperature:0.1
Inline Quality Gates:The pack invariant: a case may leave only with a non-empty superseded_by or an explicit retirement_rationale — which is what stops the pack being quietly trimmed to make a red board green. qg-L1-regression-pack-health ≥7.
Error Handling:A proposed removal failing the invariant is refused and the case stays. The pack is never left in a partially written state — writes are transactional, because a half-curated pack is worse than a stale one.

4.3 Quality gates — and why they are not guardrails

A guardrail runs on every invocation and asks is this output legitimate? A quality gate runs at a stage boundary and asks is this stage finished? Conflating them produces either a gate nobody can pass or a guardrail nobody notices.

Quality gateAssertsFires atScenario
qg-L1-test-strategy-quality ≥7Every tier declares entry and exit criteria; every governance threshold is a number, not proseEnd of T-AGreenfield only
qg-L1-test-case-ac-coverage ≥8Every AC clause maps to ≥1 case, and every compliance-tagged clause to ≥1 adversarial caseEnd of T-CGreenfield · Brownfield
qg-L1-verification-ref-integrity 100%Every Work Unit's verifier existsT-C → decompositionGreenfield · Brownfield
qg-L1-characterisation-coverageEvery GAP behaviour in the blast radius is pinned, green against unmodified codePre-constructionBrownfield only
qg-L1-repro-test-validityThe reproduction test fails, for the stated reason. A hard boolean — a repro that does not fail is not a weak spec, it is no specBefore triageBugfix only
qg-L1-feature-test-pass 100%The feature's own pack is greenFeature exitAll three
qg-L1-contract-conformance 100%The running service matches every published pact — this is what proves the resolved view T-D generated againstFeature exitGreenfield · Brownfield

The strongest guardrails in this design constrain what an agent may read, not what it may write. scenario-writer and adversarial-case-writer are denied the source, the contract and the HLD; case-writer is denied everything except the scenarios; script-generator is denied the base and the delta separately and handed only the composed view. None of these are output filters — they are enforced by the context assembler, which builds each agent's prompt from an allow-list declared in its spec.yaml.

This matters because an output check can only catch a mistake that is visible in the output. A scenario derived from openapi.yaml looks perfectly well-formed: it cites a real endpoint, it passes schema validation, and it is useless, because it can only assert what the implementation already claims. No downstream guardrail can detect that. The only reliable control is to never put the contract in that agent's context — and denial is the one control that cannot be argued around by text arriving inside the context it governs.

Two guardrails exist specifically because this is an agentic system, and would be unnecessary in a human process. gr-L1-test-immutability exists because an agent handed a red suite has exactly one cheap move — weaken the assertion — and unlike a person it feels no professional discomfort in taking it. The pack invariant inside gr-L1-consistency-check exists for the same reason at the other end: a case may leave the pack only with a superseded_by or a named retirement_rationale, which is what stops the pack being quietly trimmed to make a red board green. Both defend the oracle against the system that is supposed to be serving it.

7. Evaluation Strategy

How we will know it works before it goes anywhere near production. The test dataset must exist before development starts.

AspectDetail
Test Dataset3 replayed historical feature cycles (one per scenario) with their real AC, architecture at the version in force at the time, and the cases QA actually wrote — plus 120 labelled historical failures for triage. Labelled by two QE engineers independently; disagreements adjudicated by the QA Expert and retained as a third class, because a failure two experts classify differently is exactly the case the agent will also find hard.
Golden SetThe compliance-tagged subset: every AC clause carrying a regulatory obligation, and the adversarial case each must yield. Must never regress. Signed off by the QA Expert and the Regulatory owner jointly — the one sign-off in this design requiring two names.
MetricsPrimary: triage verdict precision ≥0.90 · AC-to-case coverage ≥8/10 · adversarial yield ≥1 per compliance-tagged clause · verification_ref resolvability 100%.
Secondary: script executability on first run ≥0.85 · duplicate-case rate at promotion ≤0.05 · fabricated-citation rate ≤0.02.
Quality GatesBefore staging: all four primary metrics met on the replayed cycles, 0 PII detections across every generated fixture, and 0 golden-set regressions. Before production: 4 consecutive shadow cycles with triage precision ≥0.90 and no QA-overturned test_defect verdict.
Evaluator AgentL1-quality-verifier scores generated cases against a rubric of AC traceability · polarity balance · citation validity · tier appropriateness. It does not score the triager — triage is scored against the labelled set, because an LLM grading another LLM's classification shares its blind spots.
Edge CasesAC with no testable assertion · a feature with zero adversarial surface · a 400-case pack against a 20-minute window · a contract delta whose from_version has moved · an architecture section added mid-cycle · anonymised production data with a broken foreign key · a characterisation pin that is red on arrival · an empty regression pack (cycle 1) · a service with no consumers · an adversarial prompt embedded in an AC clause or a Jira description.
Human BaselineThe bar to beat, measured over the last two PIs: ~62% AC-to-case coverage, ~1 in 5 compliance clauses with any negative case, triage by the engineer who wrote the code (so test_defect is over-called), and a regression pack that grew every sprint and was never curated. The design's real target is not accuracy — it is the two things the manual process structurally cannot do: adversarial coverage and a pack that can shrink.

The prompt-injection edge case is not hypothetical. Acceptance criteria, Jira descriptions and pact files are written by people outside this workflow and flow directly into agent context. Every one of those is data, not instruction. Agents that read them run with instruction-hierarchy enforcement, and gr-L1-citation-verifier provides the structural backstop: an agent that has been talked into inventing a rule cannot cite a section that exists.

Deployment TargetAgent runtime on the SFI agentic platform, delivery cluster. Three environments: dev (agent development), staging (shadow runs against real cycles), prod (the delivery pipeline itself).
PackagingPer agent: spec.yaml, instructions.md, output_schema.json, evaluation.md, examples. Plus: the six KB files, three workflow definitions (one per scenario), integration configs, and the guardrail bindings. Prompts and KBs version independently of the workflow — a prompt fix must not require a pipeline release.
Staging ValidationShadow mode across 4 consecutive real feature cycles. Agents run on live inputs and write to a parallel namespace; QA continues authoring by hand. Every cycle, the two outputs are diffed and the deltas reviewed. Nothing the agents produce reaches a Work Unit.
Rollout StrategyStaged by stage, not by percentage, because these agents form a chain and a half-enabled chain has no meaning.
Wave 1 — T-B and T-F reporting: fixtures, stub registry, coverage and traceability. Lowest blast radius; nothing blocks on them.
Wave 2 — T-C authoring: scenarios, adversarial, cases. QA reviews every case before it binds, with the review requirement relaxed once AC coverage holds ≥8 for two cycles.
Wave 3 — T-D and T-E: scripts, execution, contract verification. defect-triager runs in advisory mode first — it posts a verdict, a human routes.
Wave 4 — triage routing becomes automatic for code_defect, data_defect, env_defect and flake. test_defect stays human-confirmed indefinitely — it is the one verdict that can quietly erode the oracle.
Thresholds start tight and relax on evidence: flake threshold 0.05 → 0.10 after two clean cadence beats; triage auto-route only above 0.90 measured precision.
RollbackA single feature flag per wave, flipped in the workflow config, returns that stage to manual. Tested in staging at every wave boundary, not assumed. No agent output is destructive: cases are additive, the pack invariant prevents silent removal, and the stub registry is regenerated from the architecture rather than mutated — so rolling back never has to restore state, only stop writing.
MonitoringPer agent: invocation count, p95 latency, token spend, schema-failure rate, guardrail-trip rate. Per workflow: verdict distribution (a sudden shift in test_defect share is the early signal of oracle erosion), pack size vs the cadence window, and time-to-first-red on a newly promoted case.
Cost envelopeDominated by the per-cycle stages. At ~340k tokens per feature cycle across T-C/T-D/T-E and ~180k per cadence beat, a 4-cycle PI with 2 beats is ~1.7M tokens. The cost control is the risk selector, not the model choice — an uncurated pack costs more in runner minutes than every LLM call combined.

10. Artifact File Structure

The files this design will produce, laid out as they will appear in the repository. Every asset name follows the CoE naming standard; the use case ID is carried as metadata, not as a name prefix — see 10.1 for why.

10.1 Naming compliance — and one conflict, resolved

This template and the CoE naming standard disagree, and the disagreement has to be settled rather than split. The template says “naming follows the use case ID so artifacts are traceable to the intake”, which would give SFI-AG-QA-001-testing-case-writer. The standard says an agent is L1-{phase}-{function}, giving L1-testing-case-writer. An asset cannot have two names.

Resolved in favour of the standard, because these are L1 enterprise assets. Sixteen of the nineteen agents are generic SDLC testing agents that any SFI project will reuse; naming them after the intake that happened to fund them would make a shared asset look project-owned and would break the inheritance model the moment a second project extends one. The use case ID moves into spec.yaml as use_case_id: SFI-AG-QA-001, which preserves the traceability the template is actually asking for without putting an intake reference in a reusable asset's name.

Complete before development begins. An unchecked box is a decision still outstanding.

☑TraceabilityEvery objective and NFR in the requirements document maps to something in this design
☑AgentsEvery agent has one responsibility, and no agent is doing two jobs — the curator is the only multi-invocation agent, and its three modes share one accountability: it is the sole writer of the pack
☑AgentsEvery LLM agent has a stated model, temperature and token budget with headroom — highest is 28% of a 200k window

☐ReviewDesign walked through with the QA Expert and the Tower Representative — they recognise their process in it

Seven boxes are open, and they are the honest state of this design rather than an oversight. Four are sequencing — KB sizes, the labelled set and the walkthrough cannot be completed before the KBs are written and the review is scheduled. Two are genuine blockers that should stop development starting: the brownfield anonymisation routine has no Data Protection sign-off, and three integrations have no granted access. Building against a pending integration produces an agent that has never once run end to end.

12. Design Sign-Off

Design is signed off before development begins. Changes after sign-off follow the change request process.

Five signatures, and two of them are not formalities. The Enterprise Architect signs because this design reads APP-3, CON-*, SEC-* and REQ-* live and turns them into blocking gates — if those sections are not written to be read that way, this workflow will assert the wrong things confidently. Data Protection signs because brownfield fixtures derive from anonymised production data, which is the one place in this design where real personal data is handled rather than merely excluded.
